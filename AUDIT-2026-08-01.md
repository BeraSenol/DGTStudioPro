# DGT Studio Pro — external audit, 1 August 2026

Read against `c540d4f` ("Record M8"), tree clean, 217 sources confirmed by
`git ls-files`. Audited from source, not from the documents — the documents were
read first and then treated as claims. Two reference bodies: a chess-programming
discipline file (perft, movegen, notation, DGT serial, UCI hosting) and a
current-Apple-platform file (Swift 6.3 shipping / 6.4 and Xcode 27 beta, as of
28 July 2026).

Every finding carries what would falsify it, because a finding that cannot be
wrong is the thing this project spends most of its energy hunting. Nothing here
is claimed green; where a finding needs a run to settle, the run is named and
the expected number stated.

**Sections One and Two were written before ⌘U was run.** Section Zero below was
added after, and it changes the standing of A1 from an argument into a worked
example.

## Zero — the ⌘U run of 1 August, and what it means for the rest

Nine UITest failures, two warnings. The warnings are the registered
`Binding(present:)` waiver at its expected count of two — nothing new.

### A hypothesis that was tried and is disproved — recorded, because a ruled-out cause is worth more than an untried one

The first reading of the Players trio was shadowing. M8 turned `ProfileSection`'s
`Section` into a `CollapsibleSection` and left
`.accessibilityIdentifier(playersInspectorProfile)` on the result — no longer on
a `Section` but on a composite `View` whose subtree contains
`playersRenameButton` and `playersActionsMenu`. The failures read
`No matches found` rather than "not hittable", which is the signature of an
element that is absent rather than covered, and a discriminator across the three
inspectors fitted exactly:

| Inspector | Identifier placement | Header controls | Result |
|---|---|---|---|
| Players `.playerProfile` | on the `CollapsibleSection` | pencil + menu **inside it** | **three failures** |
| Rankings `.rankingProfile` | on the `CollapsibleSection` | none | passes |
| Library `.pgn` | on inner content and on the button | copy glyph | passes |

**`.accessibilityElement(children: .contain)` ahead of the identifier changed
nothing.** All nine failures reproduced identically. The change was reverted
rather than left in: an unverified modification carrying a confident doc comment
is the exact defect the rest of this document is about, and shipping one inside
an audit of unchecked claims would be the joke telling itself.

So shadowing-by-wrapping-identifier is **out**, and the discriminator table above
is a coincidence of shape rather than a cause — which is itself worth knowing,
because it was persuasive. Three inspectors, one difference, one failure set:
that is the form a real finding takes, and here it was pattern-matching against
the diff that happened to be in front of me.

What survives from it, and is independently checkable: the pencil and the menu
**render** — `selectPlayer` waits on `playersInspectorProfile` and that assertion
passes before line 319 fails, `continueAfterFailure` is `false`, and the empty
branch carries `playersInspectorEmpty` rather than the profile identifier, so a
resolved `playersInspectorProfile` proves `stats != nil` and a rendered
`ProfileSection`. The controls exist on screen and are not addressable by
identifier. Cause unknown.

### What M8 did and did not touch

**The line above the identifier asserted** — "Stays on the section, not the
header, so it keeps naming what the UITest expects it to name" — written in the
pass that stopped running the UITest. `DGTStudioProUITests.swift` does not

that if the finding transferred, one test would name it instead of three failing
obscurely." It worked exactly as designed. It named the cause in one line and
three failed obscurely beside it. What did not happen is anyone running it.

**Six failures are not explained by M8's diff at all** — the three view-mode
segments, the tag editor sheet, the load-error card, and the orphan-sweep alert.
The toolbar, sidebar, destinations and tag editor received only preview-
environment lines and comment edits in that range. So either they predate M8 —
in which case the "⌘U green at both review points" in the M8 record was the unit

**Confirmed in the wild, 2 Aug:** a pasted run log showed exactly this class —

The one environmental candidate M8 introduced is the second `WindowGroup`

### Two instruments, in this order, before any further fix

Both were reached for only after a guess had already been shipped and reverted.
That ordering was the mistake, and it is the same one the rest of this document
catalogues: a plausible mechanism, a confident comment, no measurement.

**One — see the tree instead of inferring it.** XCUITest will print the whole
accessibility hierarchy, and it answers in one run what four paragraphs of
reasoning could not: whether `players.inspector.rename` is absent, present under
an unexpected element type, or present and unaddressable.

```swift
// temporary, in test_players_profileHeaderControls_areHittable,
// immediately after the selectPlayer assertion
print(app.debugDescription)
```

Read it for three things: does the string `players.inspector.rename` appear at
all; what element type and depth is the profile section; and whether the header's
controls appear as siblings of the rows or are missing entirely. If the string is
absent from the dump, the cause is app-side and the search moves to why the
header's identifiers aren't applied. If it is present, the cause is query-side
and `element(_:)`'s `descendants(matching: .any)` is the suspect.

**Two — split the nine.**

```bash
git worktree add /tmp/pre-m8 f64b8d4
```

Run the UITest suite there. Same six non-Players failures → they predate M8, and
A4 below extends to the UITest target. They pass → the second `WindowGroup` is
the only candidate left, and commenting it out is a one-line confirmation.

Do instrument one first. It is cheaper, it is scoped to the three failures whose
cause is genuinely unknown, and it is the one that stops the guessing.

**Unrelated, found in the same `git status` and left alone deliberately:**
`PlayerCardView.swift` is modified in the working tree, not by this audit —
`.lineLimit(2, reservesSpace: true)` has become `.lineLimit(2)`. The comment
three lines above it says the reservation exists because "the two destinations
sort differently, so the same player got two heights. Two lines, always."
Dropping `reservesSpace` removes precisely what that comment says it is for, and
the comment is now false. Not reverted, because it may be deliberate — but it is
an uncommitted behavioural change contradicting its own doc, sitting in the tree
during a pass, which is the pattern rather than an exception to it.

## Nought — what checked out

Stated first because the greps below are only credible if the clean runs are
reported too, which is this project's own `.disabled(…)` argument.

- **The tree matched its own claim, for the first time in seven passes.**
  `caae1d7` clean, 217 sources, 135/81/1 split — all as recorded. The document's
  header says the streak resumed at one; it is at two.
- **All twelve perft reference numbers are transcribed correctly.** Six at
  depth 4 in `PerftTests`, six at depth 5 in `PerftDeepTests`, checked
  digit-by-digit against the canonical table. No transcription error, which is
  the failure mode that makes a perft suite worse than useless.
- **The DGT piece-code table is right, and it is the one everybody gets
  wrong.** `DGTPiece` is pawn, **rook, knight**, bishop, **king, queen** —
  rook before knight, king before queen, against the P N B R Q K muscle memory
  of every other chess codebase. Guarded by an exhaustive `switch` rather than
  a raw-value-indexed table, with the reason written at the site.
- **`Square+DGT` is a rank flip, not `63 - index`.** The trap is that the wrong
  version is *also* file-mirrored, looks almost right in the start position, and
  is obviously wrong the moment a piece moves. Correct, with a bijection test.
- **`/dev/cu.*`, with the carrier-detect reason written down.** The single most
  common "serial just hangs" report on macOS, pre-empted at
  `DGTSerialDevice.swift:11`.
- **`DGTFramer` resynchronises on the MSB.** Garbage before a frame is skipped,
  a corrupt length field drops and resyncs rather than buffering unboundedly,
  and unknown message bytes still frame. This is the correct shape and most
  implementations don't have it.
- **SAN disambiguation is legality-based.** `disambiguator(for:)` filters
  `legalMoves()`, not pseudo-legal ones — so a pinned second knight correctly
  produces `Nf3` rather than `Ngf3`. This bug ships silently in most GUIs and
  only surfaces when diffing against a reference PGN.
- **Castling checks all three conditions.** Rights, emptiness, king not
  currently in check (`GameState+MoveGeneration.swift:325`), transit square not
  attacked — with destination safety correctly delegated to the legal filter
  rather than restated. Plus the rook-on-home-square guard for FEN-parsed
  positions, which is a real hardening and not a defensive tic.
- **Castling rights are revoked on rook capture at its home square**
  (`GameState+Applying.swift:61-70`). The clause with no corresponding move by
  the side losing the right, and therefore the one that gets forgotten.
- **The `stop`/`bestmove` race is handled by generation counting.**
  `staleBestMovesOwed` discards both the stragglers and the orphaned
  `bestmove`. Most homemade GUIs attribute the old `bestmove` to the new
  position.
- **The `@State` macro trap has zero exposure.** Xcode 27 turns `@State` into a
  macro and forbids assigning, from inside `init`, to a `@State` property *that
  carries a default value*. Nine sites use `_x = State(initialValue:)`; all nine
  declare without a default. Nothing to do — but see A5, because a checked
  negative belongs in the forward notes.

## One — chess correctness

### C1 · The move generator's last change post-dates the last moment deep perft could have run by itself
**Severity: high. Cost to close: one run.**

Three dated facts, each from `git log`:

| | |
|---|---|
| `.tags(.slow)` landed on `PerftDeepTests` | 26 Jul, `e40d429` |
| Both test plans skip `.slow` | `DGTStudioPro.xctestplan`, `DGTStudioProUnitTests.xctestplan` |
| `GameState+MoveGeneration.swift` last changed | **28 Jul, `ab33bdf` ("Optimizations")** |

So the depth-5 suite was already excluded from every plan two days *before* the
last change to the generator it certifies. `ab33bdf` is not a cosmetic commit —
the 28 July triage attributes the rook-home castling guard and the ASCII FEN
guards to it, and the legal-filter's cached-king-square optimisation
(`GameState+MoveGeneration.swift:59-80`) is exactly the class of change that is
subtly wrong or perfectly right with nothing in between.

Nothing in the repository records a depth-5 run after `ab33bdf`. The file's own
doc comment says the optimisation "measurably cuts perft time, especially at
depth 5", which implies a run — and inferring a run from a comment is the
species of claim D43′ and D44′ exist to distrust.

**The exposure is genuinely modest and should be stated that way.** Depth 4 on
all six runs on every ⌘U, and Kiwipete at depth 4 is 4,085,603 nodes dense with
castling, pins and en passant from move one. The reference discipline's "passing
proves almost nothing" is aimed at the *starting position*, where no castling
occurs before depth 7 — it does not describe Kiwipete. What is unverified is the
top of the range, where en-passant discovered check and the horizontal pin live.

**What would falsify this:** a recorded deep-perft run after 28 July. If one
happened, the finding is a documentation gap rather than a coverage gap — and
recording it is the fix either way.

**Remedy, two parts.** Run the suite once from the test navigator (its header
budgets 10–25 minutes) and record the date and commit. Then a working
agreement, because the structure is already right and only the *trigger* is
missing: **a change under `Chess/` is not landed until deep perft has run once
against it.** The reference discipline's own shape is "a fast set every build, a
slow set before a release"; this project has no release, so the milestone
recording is the only event that can carry it.

Expected, for the run: 4,865,609 · 193,690,690 · 674,624 · 15,833,292 ·
89,941,194 · 164,075,551.

### C2 · There is no `divide`
**Severity: medium. Cost: ~15 lines.**

If C1's run comes back wrong, the whole diagnostic budget is one wrong number
and a 20-minute recursion. `divide` — per-root-move subtree counts, compared
against `stockfish go perft N` — converges on the offending position and move in
`log(nodes)` steps rather than by inspection.

The point of building it now is that writing it *during* a failure means writing
a debugger on top of the move generator currently under suspicion. The engine
binary is already bundled, so the oracle side costs nothing.

Reference divide for the start position at depth 5 is in the discipline file;
`a2a3 = 181,046`, `e2e4 = 405,385`, `g1f3 = 233,491`, total 4,865,609.

### C3 · Position 4's mirror is not tested
**Severity: low. Cost: one `@Test`, no new numbers.**

`r2q1rk1/pP1p2pp/Q4n2/bbp1p3/Np6/1B3NBn/pPPP1PPP/R3K2R b KQ - 0 1` is Position 4
mirrored, with identical counts at every depth. Confirmed absent — the string
appears nowhere in the repository. A mismatch between a position and its mirror
is a colour-asymmetry bug (pawn direction, ep rank, castling-right indices) and
localises instantly, which is the only diagnostic in the whole perft family that
names its own cause. Free to add: same expected values as `position4`.

### C4 · The full board dump is requested exactly once, ever
**Severity: high. This is the one I would fix first.**

`DGTCommand.sendBoard` appears in production at exactly one line —
`DGTConnection.swift:376`, inside `runInitSequence`. After that, `physicalBoard`
is patched one square at a time by `fieldUpdate` for the remainder of the
session (`DGTConnection.swift:425-427`). There is no periodic re-dump, and no
re-dump on reconciliation failure. I grepped every occurrence; the others are
all in tests.

The standing invariant is **"The mirror renders the physical board. Always."**
That is only true if the field-update stream is lossless. It isn't — and this
codebase already concedes the point, because `DGTFramer`'s MSB resynchronisation
exists precisely because USB-serial adapters drop bytes. The framer recovers the
*stream*; nothing recovers the *state* the dropped message would have carried.

The consequence chain is worth writing out, because each link is already built:

1. One `fieldUpdate` is lost. `physicalBoard` is now permanently wrong by one
   square, and stays wrong until reconnect.
2. The next quiescence reconstructs against a `before` that no legal move can
   reach.
3. `DGTReconstructor` returns `.unresolved` — correctly, given its inputs.
4. `enterRecovery` fires, `recordDesync` logs, and D13′ plays the alert sound.
5. The sidebar checklist asks Bera to correct a board that is already correct.

That last step is the real cost: the recovery surface is well built and it would
be pointing at the wrong thing, which is worse than no guidance.

**The remedy reuses machinery that already exists.** `handle(.boardDump)`
already replaces the whole board and republishes. So: before escalating to
`.unresolved` → recovery, send `.sendBoard` and re-reconcile against the dump;
escalate only if the *dump* also fails to explain the board. Optionally also a
periodic dump every few seconds, which the DGT command set supports without
leaving `UPDATE_BOARD` mode — `sendBoard` does not change the mode, which is
what makes the resync strategy free.

Structurally this is a nice fit for the existing design: it turns
`.unresolved` from "a settled board no legal move explains" into "a settled
board no legal move explains, *confirmed against ground truth*", which is
strictly the claim recovery wants to make before it takes over.

**What would falsify this:** a re-dump path I missed. I grepped `sendBoard`
repo-wide and `port.send` within `DGT/`; production has one call site each.

### C5 · A fail-soft bound is stored as if it were an evaluation
**Severity: medium, latent. Cost: ~4 lines.**

`UCIProtocol.swift:88-90` recognises `lowerbound` / `upperbound` and `break`s:
"Aspiration-window qualifiers on `score`; no payload." True about the payload,
and it misses what the qualifier *does* — it disqualifies the value. These
tokens arrive *after* `score cp N`, so `info.score` is already set by the time
the parser reaches them, and the qualifier is discarded rather than applied.

Downstream, every scored `info` line is yielded
(`StockfishEngine.swift:582-589`), and the driver assigns each emission to
`pgn.evaluations[index]` with last-write-wins, saving per ply
(`GameAnalysisDriver.swift:236-238`).

**Being fair about today's exposure:** under a `go depth N` that completes
normally, Stockfish's last line at depth N is the settled, unbounded one, so the
stored archive is probably clean. The defect is that nothing downstream *can*
filter, because `UCIInfo` has no way to say "bound" — so the correctness rests
on a property of one engine's output ordering under one search mode, which is
the kind of thing that stays true until the search mode changes.

Fix: a `scoreIsBound` flag on `UCIInfo`, set by the two cases, and
`guard !info.scoreIsBound` at the yield.

### C6 · `Evaluation` carries no depth, so an interrupted analysis is indistinguishable from a converged one
**Severity: medium. This is a decision, not a bug.**

`Evaluation` is `.centipawns(Int) | .mate(Int)` and nothing else. The driver
writes every progressive-deepening emission to the same slot and saves per ply,
which is what makes the graph animate the search converging — a good effect. But
a pass that is cancelled, or whose engine dies, or that meets batch analysis's
"Stop All", leaves the last emission persisted with no record of what depth
produced it.

Those numbers are then rendered as fact in two places built since:
`EvaluationBarReading` (D33′) and the graph window (D46′), both of which project
through `whiteWinProbability` and neither of which can say "this ply is depth 4
and its neighbours are depth 18".

The honest options are a stored depth alongside the eval (schema, and it makes
the graph able to show its own confidence), or a recorded decision that partial
evaluations are acceptable and a re-analysis overwrites them. The second is
probably right for a personal archive. What is not right is the current state,
where the question has never been asked and the surfaces that consume the answer
have doubled since M3.

### C7 · A `[SetUp "1"]` / `[FEN "…"]` game imports clean and then fails everywhere
**Severity: medium. Cost: one refusal, matching an existing one.**

Neither `SetUp` nor `[FEN` appears anywhere in the repository. The movetext
scanner's own comment states the premise plainly — "the movetext scanner has no
notion of SAN shape — every token that isn't a result token becomes a move" —
which is exactly why `multipleGames` is refused at the door.

A game starting from a non-standard position takes the same path and is *not*
refused. It parses, hashes, dedupes, and lands in the Library. Then every
consumer that replays from `GameState.starting` fails:

- `GameClassification.specialCheckmate` swallows it in `try?` and returns `nil`
  — silent, and indistinguishable from "an ordinary mate".
- `ECOClassifier` still names an opening, because it is pure string matching
  over moves that mean something else entirely. A Ruy Lopez name on a position
  that never was one.
- The analysis driver stops at the first ply with "won't parse — analysis
  stopped there", which names the ply and not the cause.

Adjourned games, position exercises, and anything exported from a study carry
`SetUp`/`FEN`. Refusing at the import door with a message naming the tag is the
same shape as `multipleGames` and the same honesty: refuse until a real importer
exists. Adding it also removes the ECO-classifies-a-fiction path, which is the
worst of the three because it produces a confident wrong answer rather than a
gap.

### C8 · PGN reading is UTF-8 only
**Severity: low-medium. Cost: two lines.**

`PGNStore.swift:120` — `String(contentsOf: url, encoding: .utf8)`, no fallback;
failure surfaces as `Error.fileReadFailed`, which reads as a disk problem. The
PGN standard says ISO 8859-1; reality is UTF-8, sometimes Windows-1252,
occasionally mixed inside one file — and player names are where the non-ASCII
lives, which is this app's whole identity story (D9′ deliberately preserves
diacritics; "Bücher" ≠ "Bucher").

Try UTF-8, fall back to `.windowsCP1252`, which never fails and is therefore
safe as a last resort. Only bites third-party imports — the app's own exports
are UTF-8 by construction.

### C9 · The `endedInMate` open item appears to be unreachable, and therefore cheaper than recorded
**Severity: informational — an item that shrinks.**

The standing open item says `GameRecord.endedInMate` spells the mate question
`hasSuffix("#")` while D18′ and `GameClassification` spell it `contains("#")`,
so `Qd2#!` reads as mate to one and not the other; and that changing it "moves
every saved Checkmate tag's matching, a D30′-shaped decision rather than a
rider."

There are four writers of `PGN.moves`, and all four canonicalise:

| Writer | What it stores |
|---|---|
| Import (`PGNParser:106`) | `flushToken` → `stripAnnotations`, which strips trailing `!`/`?` in a loop |
| Archive | `game.sanMoves`, produced by `san(for:)` — never annotated |
| Movetext edit (`PGNStore:247`) | `MovetextEdit.Accepted.moves`, canonical `san(for:)` per ply |
| `UITestSeed:111` | hand-written literals, already canonical, UI-test only |

So no stored move can carry a character after `#`, and the two spellings agree
on every row in the Library. The item is a real code divergence with — as far as
I can see — no observable consequence, which downgrades it from a decision about
tag matching to a one-line unification or a comment saying why two spellings are
harmless.

**What would falsify this:** a fifth writer, or an import path that reaches
`PGN.moves` without `flushToken`. The grep is
`grep -rn '\.moves = \|moves: moves' --include=*.swift DGTStudioPro/` — worth
running before acting, because the whole point of the finding is that nobody
ran it.

### C10 · Two smaller ones, recorded rather than argued

**The en-passant target is emitted permissively.** `updatedEnPassantTarget` sets
the target after any double push, regardless of whether a capture is actually
available. This is correct and harmless *here* — the app has no repetition
detection and no position-keying, so nothing consumes the distinction. It stops
being harmless the moment threefold or a position hash appears, because FIDE
defines "same position" to include en-passant availability and the permissive
convention makes genuinely repeated positions look new. One sentence at the
function, per the discipline's rule that the next reader will assume the other
convention.

**The `(from, to, promotion)` uniqueness invariant is sampled at five root
positions.** `MoveFootprintTests` checks five FENs at depth 0, and
`DGTReconstructor` relies on the invariant at every position of every game. It
holds as a theorem in standard chess and the suite has a proper anti-vacuity
guard (`promotionPositionActuallyExercisesTheCollisionPath`), which is the
discipline applied exactly right. Strengthening is nearly free: run the same
key-collision check at every node of a depth-3 perft walk, which turns a sample
into a few hundred thousand cases and costs seconds.

## Two — architecture and the decision record

### A1 · Four written rules have prevented the uncommitted-tree failure zero times; the command has caught it six of six
**This is the highest-leverage item in the audit.**

The document says this itself, and draws the right local conclusion ("stop
expecting the prose to work"). The conclusion it hasn't drawn is that **every
check in the sweep is already a one-liner, and none of them is a script.**

Take the five species of unchecked claim now catalogued, and what each would
have cost as a shell line:

| Species | The pass that found it | The check |
|---|---|---|
| The tree is clean | six of seven passes | `git status --porcelain` |
| The file is there | D42′ (`.swift-format`) | `git ls-files` |
| The number is current | D43′ (295 warnings) | the cold-build invocation the document already records **verbatim** |
| The set is complete | M8 (8 of 15 headers) | one `grep -c` against one `grep -c` |
| **The check still covers it** | **Section Zero, 1 Aug** | **`git diff --stat <base> HEAD -- DGTStudioProUITests/`** |

The fifth is the sharpest of them, because the check that would have caught it
was not merely available — it was *written for this*, named in the waiver
register as the canary for this exact shape, and it fired correctly the first
time it was allowed to run. A milestone whose gate says "the full UITest suite
stays green" and whose diff does not touch the suite is a one-command
contradiction.

All five are written down as prose, in a document that argues — in its own
build-diagnostics section — that **"the build is the check; the memory is not."**
The same sentence applies to the sweep. A `Scripts/sweep.sh` that runs those
four plus the prohibited-token greps and the `.disabled(…)` enumeration, wired
to a scheme pre-action or a pre-commit hook, converts four remembered rules into
one command and makes the recurrence structurally impossible rather than
repeatedly regretted.

The counterargument the document would make for itself: a check that always
produces noise is a check being read past — the `.DS_Store` finding. That is an
argument for the script to exit non-zero only on real findings, not an argument
against the script.

Note also that this is the one item where the project's own precedent is
unusually strong: `CollapsibleSection` exists to make one class of defect
*unrepresentable* rather than merely unlikely (D45′). A sweep script is the same
move applied to the process instead of the code.

### A2 · The synced knowledge copy is stale again — right now, and by more than last time
**Severity: medium, and self-demonstrating.**

The tracked `ROADMAP.md` is 784 lines, last revised 1 August, with M8 in Landed.
The copy in project knowledge is 347 lines, last revised 29 July (evening), with
**M8 still scheduled and its decisions unmade** — it lists "popover anchored to
the header vs a sheet" as the open question, months of reasoning before D46′
chose a window and recorded why both alternatives were wrong.

So anyone starting a pass from the synced copy would re-derive a decision that
has been made, in the exact shape D44′ was burned by. The same holds for the
instructions: the synced doc is dated 29 July, four D-numbers behind.

This is not housekeeping. The document already names the remedy correctly — "the

### A3 · `PerftDeepTests` gives the twin-read-site pattern as its own justification
**Severity: low as a defect, high as a signal.**

`PerftDeepTests` keeps a private copy of the six FENs *and* a private copy of the
`perft` function, and both `ChessTestSupport` and `PerftDeepTests` document the
duplication as deliberate: "so the slow depth-5 re-certification can't silently
drift away from the canonical source by accident."

That reasoning is inverted. Duplication is *how* two statements drift; sharing is
what makes drift unrepresentable. This is D25′'s twin read site with the argument
running backwards, and it sits in the one suite where a silent divergence would
mean the deep certification certified a *different position* than the shallow
one — and would still pass, because it would be checking its own FEN against its
own number.

The strings are byte-identical today; I diffed them. So nothing is wrong and the
recorded reason is the finding. Either share the fixtures (and note that
`PerftTests` already reads from `Chess`), or keep the copy and change the comment
to the honest reason, which is probably "self-contained so it can be run from a
scratch checkout" — a real reason, and a different one.

### A4 · The waiver register has no row for coverage that exists but never runs
**Severity: low. Cost: one table row.**

The register is admirably complete about types with no preview and types with no
suite. It has no vocabulary for the third case: a suite that exists, is correct,
is listed under "closed as covered", and is excluded from every test plan. Deep
perft is currently in that state, and it is the single most load-bearing suite in
the codebase — everything downstream of the generator (SAN, reconstruction,
classification, movetext validation) is noise if it's wrong.

A row saying so, with its last-run date, would make C1 impossible to acquire
again. The register's own closing line already says a new entry is a signal
worth attending to; this is one it currently cannot express.

### A5 · Two toolchain notes, both cheap, one of them a checked negative
**Severity: low, but time-boxed by the September GM re-read.**

**`@State` becomes a macro in Xcode 27**, back-deployed to macOS 14, and it is
the one item on the 27 list that *breaks a build* rather than offering an
improvement: assigning from `init` to a `@State` property that carries a default
value becomes "used before being initialized". The forward notes don't mention
it. As reported in section Nought, this codebase has **zero exposure** — all
nine init-assigned `@State` properties declare without defaults. That checked
negative is worth a line in the notes precisely because it is negative: the
whole value of D27′'s conformance sweeps is that a clean run is what makes a
dirty one credible.

**Swift Testing's warning issues and test cancellation ship in 6.3**, not 6.4 —
they are available now, on the current toolchain, and they fit two patterns the
project already has written waivers for. `try Test.cancel("…")` bails without
failing, which is exactly the New Game picker UITest that "is unreachable — the
sheet gates on a connected board and UI runs are boardless by construction".
`Issue.record(severity: .warning)` records without failing, which is the shape of
"manual checks stand in for what XCUITest can't reach". Neither is a migration;
both turn a written waiver into something the test report says out loud.

### A6 · Where the reconciliation design is better than the reference, and should be recorded as such

Worth stating because the document is scrupulous about recording where it
diverges from convention, and this divergence is unrecorded and favourable.

The standard advice for occupancy-to-move inference is: enumerate candidate
positions, compute each one's occupancy signature, scan for a match. What
`DGTReconstructor` does instead is derive `(from, to)` from the diff, index the
unique legal move with those coordinates, and *then* verify
`before.applying(candidate) == physical`. That is the same safety property —
full-position verification, not event classification — reached by lookup rather
than by scan, and it is strictly better: one verification instead of forty.

Three refinements go beyond the reference outright. Underpromotion is read off
the arrived piece rather than assumed, with the reasoning written at the site
("the square *is* the declaration"). `.correctable` handles the en-passant
capture whose taken pawn was never lifted — a very common casual slip whose diff
is indistinguishable from a plain push — as a nudge rather than a desync. And the
three mid-castle interim states are enumerated with the *fourth* deliberately
excluded, because rook-placed-first-with-king-untouched is byte-identical to a
completed legal rook move and intent is unknowable at that instant. That last
paragraph is the best comment in the codebase.

Two gaps against the reference, both minor and both decisions rather than fixes:

- **No two-ply lookahead.** In fast play two moves can complete inside one
  quiescence, and the current answer is `.unresolved` → recovery. The reference
  suggests trying the depth-2 positions before giving up. Against that: Decision
  #1 makes the physical board truth and the record append-only, so a wrong
  two-ply guess corrupts the record silently — which is exactly the failure
  Decision #1 is built to prevent. Probably correct as-is; worth being a recorded
  rejection rather than an unconsidered absence, especially since C4's dump
  request would resolve most of the same settles honestly.
- **The 300 ms quiescence is fixed.** The reference range is 100–200 ms and it
  recommends exposing it, because players differ enormously. One user, one board
  — so the argument for exposing it is weak, but the argument for writing down
  why 300 was chosen is not.
